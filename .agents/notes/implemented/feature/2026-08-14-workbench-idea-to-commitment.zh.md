# Agent Note: 工作台 —— 会话日志之上的「念头到落地」节点树

Status: implemented

[English](2026-08-14-workbench-idea-to-commitment.md) | 中文

## Problem

把一个粗糙的念头带到团队真的承诺下来，过程中的推理会一路丢掉。笔记、聊天、文档各存一部分：定了什么、否掉了什么、某个断言是从哪句话来的、还有什么没定。之前在 Markdown 文件上做过一次，失败得很具体——只要页面编辑有一点摩擦，人就绕开页面直接改文件；一旦这么做，结构和记录就静默地各走各的。

由此得出两条约束，而它们互相拉扯：

- **人的编辑必须零成本。**即时、不调模型、不等待。否则人就绕开工具。
- **模型不能写进本体。**它的产出是草稿，由人裁决。否则记录会堆满看着有道理、但没人承诺过的内容。

Harness 让这两条同时可达——会话日志本来就持久、广播、可重放——但它没有任何东西建模"陈述之树"、闸门，或者一手层。

## Decision

两个包：`packages/workbench/workbench`（宿主）和 `packages/client/workbench`（工作台 tab）。树唯一的持久化载体是会话日志，磁盘上没有第二份。

### 两条写路径，为什么不一样

人经 `workbench-edit` **命令**写入，由 tab **程序化**派发——没人手打斜杠。`commands.execute` 本来就是 Remote，命令名是运行时查注册表，所以这条路不需要新的网关方法、不需要生成描述符，也不用碰 `packages/host/apiproxy/src/api/rpc-map.ts`。handler 回 `{ kind: 'success', sourceEventSeq }`；真正的变更从 tab 本来就订阅的事件流回来，一处事实一个家。被拒时回 `{ kind: 'error', text }`，点名哪条闸门。

模型只有 `workbench_propose` 一条写路径，而草稿到不了树。它用 `workbench_read_nodes` 读，可以用 `workbench_check_promotion` 问某个节点还缺什么。**故意没有会晋升的工具**：晋升就是人做出承诺的那一刻，模型驱动的晋升正是第二条约束禁止的东西。

### 派生量住在哪

`core.ts` 把每个派生量算一次——依赖集与展开、1 跳失效、形态候选、字段登记、`rev` 步进——都是显式读模型上的纯函数，不碰 cordis、不碰 I/O。`gates.ts` 和 `edit.ts` 同样是纯的：进去一个请求和一份投影，出来要 append 的事件。

浏览器**用同一份代码**折叠事件族，经 `./projection` 这条 entry，它按**精确子路径**列进了 `packages/client/tsdown.client.ts` 的 `INLINE_SAFE`。包根会碰 cordis 和工具注册表，不是 browser-safe；那条 entry 才是纯层。另一条路——在客户端重写一遍折叠——正是上一次尝试犯过的错，同一个事实因此有了两个值。

### 事件族

`workbench/snapshot` 是完整的整值检查点：节点、一手层、proposal。它没有自己的 `rev`（`meta.rev` 就是树的），而"完整"是故意的——缺一手层的检查点会让冷启动跳过那段前缀，而树上字段引用的条目就在里面，之后每个用到它的依赖集都建不起来。

`workbench/node-change` 是唯一的写事件；一次提交写 N 个节点就发 N 条、共享一个 `rev`。`workbench/utterance` 是一手层。`workbench/proposal` 与 `workbench/verdict` 承载草稿与裁决。

**任何会话的第一个 workbench 事件都是检查点。**浏览器把这一族折叠成一个 Context，start 是检查点，所以三条 append 路径——镜像、编辑命令、propose 工具——都先调 `ensureCheckpoint`。少了它，折叠会收到一个没有 state 可更新的 update，整个 Context 在这个会话里就废了。

### 一手层镜像

自定义会话事件永远进不了模型请求，所以人的话要走两趟：一趟是模型读的 `user/message`，一趟是树引用的 `workbench/utterance`。镜像是一手层条目的**唯一**生产者——正因为唯一，"每条消息恰有一条条目"才能是不变量而不是期望。`./invariant` 在每条条目落地时校验，无需 deadline：条目以它镜像的那条消息命名，所以一条进来就同时证明它的消息存在、且它之前的消息都已镜像。

append 推到微任务，因为 `session.append` 拒绝在一次 append 发布期间重入，而镜像正跑在那次发布里。

### 闸门作用在哪

工作区（念头／想法）不设闸；那里的摩擦是在给思考收税。已承诺区设闸，于是"严谨"的全部代价落在晋升那一刻：未登记的字段、没依据的取值、有子节点却从没说清自己管什么的模块，在那里不再被容忍。结构性闸门——引用都能解析、树还是树——全区生效，因为坏掉的树不是草稿。

模块无职责在普通写路径上是提示，在晋升时阻塞。采纳草稿时，闸门重跑的是**人改完的**内容而不是模型提的内容，而且人可以在提交之前剪掉和改名待建节点——所以被剪掉的节点从未进过树。

## Alternatives considered

**用网关 RPC 方法（`workbench.edit`）而不是命令。**原方案选它，理由是 `RpcMethodMap` 是产品方法的家。按证据否掉：`rpc-map.ts` 近 60 天改了 60 次、`web-app/cordis.patch.yml` 改了 88 次，而命令这条路两个都不需要。`CommandDefinition.recordInput: false` 和 `CommandResult.sourceEventSeq` 的文档写的正是这个形状——handler 落领域事件、客户端读事件流。

**在磁盘上再存一份树。**否掉：一个事实源，而日志本来就持久、广播、可重放。代价是真实的，写在下面。

**在浏览器重写折叠。**否掉，见上。

**给模型一个 `workbench_promote`。**否掉：它和"人裁决"这条约束冲突。模型拿到的是缺项清单，然后用它唯一能用的方式去补——提草稿。

**保留 `add-utterance` 这个编辑 op。**否掉：有了第二个生产者，"每条消息恰有一条条目"就弱化成"至少一条"，而弱化之后它就抓不住它本来要抓的那种静默丢失。

## Testing

`tests/acceptance.spec.ts` 在真实组装上走完两条判据——真的 agent loop、真的 DeepSeek adapter 指向脚本化 mock provider、命令注册表，以及本插件——全程无 API key。冷启动：一句话、模型提的骨架、人剪枝，以及一次被闸门拒到树能为自己作答才通过的晋升。人自己的编辑：落盘、`rev` 前进，而 provider 自己的请求记录始终为空——这让"没调模型"是可核对的，而不是断言的。

每条闸门都配了一条"注入它必须拒绝的情形"的测试。投影带着日志级的拒绝——没真晋升的晋升、追加两次的条目、落在不存在草稿上的裁决、倒退的 `rev`——各自一条。

## Consequences

- **检查点随一手层增长。**这就是"整值检查点被投影后端替换之前，会话长度的上限"。
- **失效只做 1 跳，且没人消费。**骨架索引**故意**不算作边：算作边的话，任何一次改名都会作废每一个节点。
- **作者归属只到节点，不到字段。**"树上还剩多少一字未改的模型散文"只能按节点粒度数。`structuralHealth` 量的是相关的那个趋势——正文在长而字段词汇量不长——作用在一个检查点的节点集上；这是对"模型把每个新概念都写成散文、而未登记字段闸门永远绿着"这种失效的唯一一道防线。
- **落盘之后没有一致性检查。**闸门只在写路径上跑。设计论证过：即时落盘与一致性检查要共存，异步巡检是结构性必需；本次交付的是前段加晋升门，不是完整闭环。
- **导出没有归属。**树只活在日志里，那么"从树投影出成果"就是必需项而不是加分项。
- **加第二个 view target 顶出了一处类型弱点。**`ConversationViewSnapshotStore.get<Target>` 对泛型 `Target` 把 `ConversationViewSnapshotMap[Target]` 读成交集，只有一个成员时无害。加了 `workbench` 之后，ui-trajectory 的测试桩需要一次窄化；第三个 target 会再撞一次。
