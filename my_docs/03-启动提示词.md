## 纪律（这几条比进度重要）

- **不要碰正在运行的 3080 实例。** 本机有一个 dsh web 在跑（工作区 `dsh-workplaces/test`）。
  用独立端口 3081。`dev:web` 的 HMR 会把新 client bundle 热载进正在运行的实例，
  坏的客户端插件会弄坏它。必要时用 git worktree 隔离。
- **遇到与方案冲突的 DSH 事实：先记录，再调整方案，不要硬绕。**
  新建 `my_docs/04-实现偏差记录.md`，逐条写：DSH 实际是什么／方案原本假设什么／你怎么改的。
- **新增闸门先写否证测试**：注入一个它应当拒绝的情形，确认它**真的拒**，再声称它有效。
- **派生量只在 `core` 算一次**：依赖集／失效判定／形态候选只有一个实现处，
  store／工具／客户端一律只消费。这条有实测教训——同一事实被算两遍、给出两个不同数字。
- **不许凭印象声称"通了"**：跑命令，贴真实输出。
- **未定的东西标出来，不要沉默填补**：`○` 悬空未定／`△` 我提出／`〔事实〕` 有证据附来源／
  `〔推论〕`／`〔待检验〕`。完整规范在 `90-方法论前提.md`。

## 结构上的一条建议（`02` §八）

`core`（依赖集／闸门／形态候选／rev）是**纯函数、零 DSH 依赖**。
`01` §三 把它放在 DSH 包里面——建议改成独立目录、独立可测、**不 import 任何 DSH 模块**。

理由：DSH 是预发布、API 会破坏性变更，破坏只应打到 adapter 层；
而且 core 的否证测试不需要 DSH 跑起来（`01` §十二 第一行已经这么设想了，只是包结构没照这个切）。
