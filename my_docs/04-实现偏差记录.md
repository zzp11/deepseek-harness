## D-01 客户端 roster 行：overlay 能插，但包名解析另有一套

**方案假设**：`00 §5.2`／`03 T1` —— overlay 里 `insert:` 两行即可装载；`00 §4` 另说客户端行要加进 `packages/bundle/web-app/cordis.patch.yml`。两处不一致。

**DSH 实际**：这是两件事，`02 §七-3` 把它们混成了一个问题。

1. **行本身**：overlay 插入的行就是 Loader entry，而 client-modules 的 node 半扫的正是 Loader entries（`packages/client/modules/src/index.ts` 模块 JSDoc）。所以 **roster 行不必写进 `web-app/cordis.patch.yml`**。
2. **包名解析**：Loader 从 `$DSH_HOME/profiles/web/` 解析 bare row name，client-modules 扫描器用 `createRequire(ctx.baseUrl)`（同一目录）取 `<pkg>/package.json`。两者都落到 `$DSH_HOME/profiles/node_modules` 这个回退目录，而它由 `healProfilesModuleFallback`（`packages/boot/app-boot/src/profile.ts:223`）按 **dsh app 清单的依赖闭包 BFS** 生成。不在闭包里 ⇒ `ERR_MODULE_NOT_FOUND`。

第一次跑的真实错误：

```
Error: dsh: plugin tree failed to load: failed to apply loader entry include (cordis:include):
  failed to import loader entry workbench-client (@deepseek-ai/dsh-client-workbench):
  Cannot find package '@deepseek-ai/dsh-client-workbench' imported from /Users/zzp/.dsh/profiles/web/
```

**怎么改的**：两个包加进 `packages/bundle/web-app/package.json` 的 `dependencies`（web-app 在 app 闭包里），`pnpm install` 生成链接。**没有动 `packages/bundle/web-app/cordis.patch.yml`** —— 那个 60 天 88 次的热文件躲开了；roster 行留在 `my_docs/workbench.patch.yml`。

**⇒ 对 `02 §七-3` 的部分回答**：客户端 roster 行**能**放进自己的 `--patch` overlay。真正的仓库触点从「热 YAML 一行」降级成「`package.json` 一行依赖」。剩下未验的是零仓库修改那条路：`dsh plugin --profile web add <pkg>` 把包装进 `$DSH_HOME/profiles/web/node_modules`，同样能被上面两条解析路径找到。**未做**——它会持久改用户的 `~/.dsh/profiles/web`，留给 `03` 排给 T4 的那 1–2 小时 spike。

## D-02 host 包"自己就通了"是源码启动的偶然通路，不可依赖

**DSH 实际**：`@deepseek-ai/dsh-workbench` 在加依赖**之前**就装载成功了。原因是 tsx 的 `resolveTsPathsSync` 命中 `tsconfig.base.json` 的 `@deepseek-ai/dsh-*` 通配（含 `./packages/extensions/*/src`），直接解析到源码。

`@deepseek-ai/dsh-client-workbench` 没被命中：client 组只有 `dsh-client-*/invariant` 和 `dsh-client-*/client` 两条通配，**bare name 是逐包显式列的**，新包不在列内。

**为什么不能依赖它**：这条路只在「源码启动 ＋ cwd 在仓库内」时存在。client-modules 扫描器走 `createRequire`，不认 tsconfig paths；built 启动也不认。

**怎么改的**：不为它加 tsconfig paths 显式行，改走 D-01 的依赖闭包。记下来是因为它会制造假信号——host 行看着通了，client 行才暴露真实解析规则。

## D-03 客户端插件必须先构建，源码启动也不例外

**方案假设**：`00 §2`「`pnpm dsh web --patch <overlay>`（从源码跑，经 tsx）」。

**DSH 实际**：client-modules 只 serve 构建产物 `lib/client.js`，缺了就是 `client-modules: client bundle not found; run 'pnpm run build' before launch`（`packages/client/AGENTS.md` 新包清单第 5 条也这么写）。宿主半边可以从源码跑，浏览器半边不行。

**怎么改的**：改完客户端跑

```sh
pnpm exec tsc -b packages/client/workbench
pnpm --filter @deepseek-ai/dsh-client-workbench bundle
```

首次还要一次全量 `pnpm run build`（前端 dist ＋ 各包 `lib/`）。

## D-05 客户端 `inject` 名写错是**静默**不激活

**DSH 实际**：没有 `runtime` 这个 client service。dsh-client-runtime 提供的是 `slots` / `conversationEvents` / `conversationViews` / `sessions` / `workspaces`（`packages/client/runtime/src/client/index.ts:169-179`）。`package.json` 里 `dsh.client.inject` 列的是**包名**，只用于 preflight 显示与 HMR diff，**不排序、不构成激活条件**；激活条件只有 cordis fiber 等 **service**。

## D-09 △ 一手层条目要带 `rev`，否则失效判定有个洞

**方案原本**：`01 §四` 的 `FirstLayerEntry` 是 `{ kind, entryId, text, createdAt }`，`01 §五` 的 `workbench/utterance` 载荷同样没有 `rev`。

**撞到的**：`DependencyItem.rev` 是失效判定的**唯一**依据——草稿是拿一份依赖集算出来的，任一条目的 `rev` 动过，草稿就作废。一手层条目不可改、永不过期，但"永不过期"也得有一个能比的值；没有 `rev` 就只能给 source 类目填个假数，而假数会让"比 rev"这套机制在这一类上静默失效。

**怎么改的**：`FirstLayerEntry` 加 `rev: number`（条目 append 当时的全局 `rev`）。T3 的 `workbench/utterance` 事件载荷要一起带上。标 △ 是因为这是我提的模型扩展，不在 `01` 原文里。

## ○ 实现 core 时浮出来的四条悬空未定

1. **`G-` 子树怎么表示**：`01 §七-1` 只写"`G-` 子树全部条目"。我按"约定 id 为 `G-` 的根节点，其后代即约束区"实现（`GLOBAL_CONSTRAINT_ROOT_ID`）。跟着来的问题：`parent` 只有一个，所以若 `02 §二` 的提升进阶段 0，"把节点标进 `G-` 子树"是**移动**（节点离开原模块树）还是**另建一个约束节点**？`02 §二` 没说。

## D-11 `01 §五` 的快照载荷和 `01 §六` 的冷启动断言互相矛盾

**方案原本**：`§五` 的快照载荷是 `{ rev, nodes, meta }`；`§六` 说"冷启动 = 最近快照 + 其后增量重放"。

**撞到的**：这两句不能同时成立。一手层和 proposal 都不在那个载荷里，**跳过快照之前的前缀就把它们丢了**——而树上的字段用 `sourceId` 引用一手条目，`dependencySet` 遇到取不到的引用会当场抛（`cites missing first-hand entry`）。所以照 `§五` 的载荷实现，`§六` 的冷启动会做出一棵读不了的树。

**怎么改的**：快照做成**完整检查点** —— `nodes ＋ firstLayer ＋ proposals ＋ meta`。这样 `§六` 的断言字面成立，`latestSnapshotIndex` 是真捷径而不是另一个答案。钉了两条测试：一条比"从最近快照重放 == 全量折叠"，一条专门验"被引用的一手条目活过冷启动"。

代价写进了 README 的 Known Limitations：检查点随一手层增长——这正是 D3「超长会话留 v2（SQLite 投影）」那句话的真实上限来处，之前它只是个笼统的担心。

## D-16 D1 改判：编辑通道走 `ctx.commands`，两个热文件都不碰

**`00 §3`／`01 D1`** 定的是模式 A：在 apiproxy `RpcMethodMap` 注册 `workbench.edit`。`02 §七` 提出 commands 可能免掉改仓库，但列了三条未验。**三条现在全通**：

| ○ 待验 | 结论 | 证据 |
|---|---|---|
客户端能否**程序化**调用命令 | **能** | `commands.execute(agent, line, signal)` 带 `@Remote`（`packages/interaction/commands/src/index.ts:296`）；`ctx.remote.commands.execute(sessionId, line)` 已有先例（`packages/client/ui-commands/src/client/service.ts:374`）。任何声明 `inject: ['remote', 'remote.commands']` 的客户端插件都能调，用户看不到斜杠 |
新命令是否需要仓库侧白名单／重新生成 | **不需要** | `RpcMethodMap` 里没有任何 command 方法；Remote 挂在**服务**上（`list`/`execute`），命令名是运行时查动态注册表。加一个命令＝零 wire 变更、零 typert 重新生成 |

**并且 `CommandDefinition`／`CommandResult` 的类型注释本身就是这个架构**：`recordInput?: false` 的注释写「a command whose domain event owns the payload」，`CommandResult.sourceEventSeq` 写「earlier authoritative domain event that owns a richer presentation」。上行＝命令、下行＝事件流，不是绕路，是这套 API 的设计用途。

**改判**：走 `ctx.commands.register()`。`01 §九` 的返回值 `{ ok, rev, invalidation }` 随之变成 `{ kind:'success', sourceEventSeq }` ——客户端从 `workbench/node-change` 事件读 rev 与作废清单（它本来就要订阅事件流），一处事实一个家。闸门拒绝走 `{ kind:'error', text }`。

**避开的**：`packages/host/apiproxy/src/api/rpc-map.ts`（60 天 60 次）、`packages/bundle/web-app/cordis.patch.yml`（60 天 88 次）。

## D-17 `session.append` 不能在 `session/event` 监听里重入

**DSH 实际**：`packages/core/session/src/index.ts:624` —— `if (entry?.appending) throw new Error('session append cannot reenter while another append is being published')`。

`01 §五` 的原话镜像机制（监听 `user/message` → append `workbench/utterance`）**照字面实现会当场抛**。

**怎么改的**：镜像的 append 推到 `queueMicrotask`，并由 `ctx.effect` 的 disposer 翻一个 `live` 标志给那个延后的续体看。

**连带后果（给 `02 §六` 的）**：因为镜像必然异步，"每条 `user/message` 恰有一条 `workbench/utterance`"这条**完整性**不变量没有同步的判定时机（同步的 companion 没有 deadline 可比）。落地的运行时不变量改成一条等价强度、**无需 deadline** 的形式：

> 每条到达的 `workbench/utterance` 都以它镜像的那条消息命名，所以一条进来就同时证明两件事——它的消息存在（无孤儿），且它之前的消息都已镜像（无缺口）。**漏一条会在下一条镜像落地时暴露。**

只剩"最后一条消息的镜像还在飞"这一个尾巴无法同步判定，由 `plugin.spec.ts` 的镜像用例覆盖。

## D-18 invariant 必须挂 `internal/dispatch`，挂 `session/event` 等于没挂

**DSH 实际**：会话 store 对 `session/event` 监听器的失败是**逐个容器化**的（"observer failures are logged and contained per listener"）。所以在 `session/event` 里 `fail()` 抛出的 InvariantError 被吞掉，companion 报不出任何东西——第一版就是这样，测试全绿地"通过"了。

**怎么改的**：照 `packages/core/session/src/invariant.ts` 的做法，校验挂 `internal/dispatch`（提交前，抛得出去）。副作用：那时事件还没进 log，所以 `session.events` 不含它——这一点写进了 companion 的 JSDoc。

**这条值得单记**：一个"看起来装好了、实际永远不会报"的 invariant，比没有 invariant 更危险。

## D-19 `01 §八` 与 `01 §十四` 对「模块无职责」互相矛盾

`§八` 的闸门表把它标成**提示（不阻塞）**；`§十四` 判据 1 第 5 步写的是"闸门检查：有子节点缺 duty → 返回 blocked 清单 → 人补 duty 后晋升成功"，即**阻塞**。

**怎么裁的**：两者都对，只是作用时机不同 —— **普通写路径提示，晋升时阻塞**。晋升是这棵树被要求"说清自己管什么"的那一刻，`§十四` 的验收要求也只有这样才成立。已配两条测试（同一个节点，`promoting: false` 得到 `blocking: false`，`promoting: true` 得到 `blocking: true`）。

## D-20 `add-utterance` op 删掉了

`01 §九` 的 op 列表里有 `add-utterance { text }`。**删了**：一手层现在只有一个生产者——`user/message` 的镜像。

理由是 D-17 那条不变量：只有当镜像是**唯一**生产者时，"每条消息恰有一条条目"才是精确的；再开一个能凭空追加条目的 op，这条不变量就只能弱化成"≥1"，而弱化之后它就抓不住"静默漏"了 —— 那正是 `02 §六` 要它防的东西。

## D-21 浏览器里手打斜杠**到不了**命令通道

试图在 3081 的 composer 里手打 `/workbench-edit {...}` 验证端到端，结果那行**被当普通消息发给了模型**（模型开始读我的源码，跑了一轮才被我掐掉，花了真实 API 额度）。

〔事实〕`ui-commands` 的拦截走的是 `inputTriggers` 那条按键触发的 `/` 弹窗管线，不是"提交时解析这行文本"。填入文本再回车绕过了触发检测。

**这对方案是好消息**：`02 §七` 担心的"文本体验差"根本不存在——命令**只能**程序化调用（`ctx.remote.commands.execute`），人手打反而进不去。用户永远看不到斜杠不是设计取舍，是这条通道的默认行为。

**代价记一笔**：验收走查里不要用手打命令行当证据。

## D-22 一处比 `01` 更严的拒绝：`delete` 不允许留下孤儿

`01 §八` 的悬空引用闸门管的是写入者自己的引用。但删一个有子节点的节点，会把**别人**的 `parent` 变成悬空——闸门看不到，因为被删的节点不在候选集里。

**怎么改的**：`delete` 先拒绝有子节点的节点（"先把它们移走或删掉"）。这是请求级拒绝而不是闸门，因为它不是内容不合法，是这一步做不到。

## D-23 `workbench_promote` 改成 `workbench_check_promotion`（不写）

`01 §十-3` 让 AI 有一个会 `append node-change(op:'promote')` 的工具。**这和 `§一` 的铁律直接冲突**——晋升是把节点变成"已承诺"，即人做出承诺的那一刻；`10 §14` 判据 1 第 5 步和 `01 §十四` 的走查里，晋升都是**人**点的。

**怎么改的**：第三个工具改名 `workbench_check_promotion`，只报"过不过晋升门、缺什么"，**不写**。晋升只有人的 `promote` op 一条路。这样铁律精确成立：模型到本体没有任何写路径，只有 `propose`。名字也改了——叫 `promote` 却不 promote 是给模型的误导性契约。

## D-24 冷启动死锁：树空的时候模型拿不到任何 nodeId（**真实 LLM 端到端跑出来的**）

`01 §十` 把骨架索引放在依赖集里，而依赖集要**先给一个 nodeId**。于是冷启动时模型无路可走。

〔事实〕真实 DeepSeek 在 3081 上的第一次运行：它调 `workbench_read_nodes` 猜了个 id，拿到 `Error: workbench: no node G-`，然后**去翻我的源码和会话日志找 id**，烧掉 288K 输入 token 也没提出一份草稿。

**怎么改的**：`nodeId` 改成可选。不传就只返回全局约束 ＋ 整棵树的索引（空树就是空索引，是个可读的答案，不是错误）。`requireNode` 的报错也改成指向这条路。系统提示词第一条改成"先不带 nodeId 调一次"。

改完重跑：模型第一步就是 `workbench_read_nodes · {}`，看到空树，直接提出 5 个顶层节点的骨架。**这个洞只有真实模型跑得出来**——mock 和单测都会按我以为的顺序调。

## D-25 一手层镜像必须先落锚点检查点（**浏览器端到端跑出来的**）

客户端把 `workbench/*` 折叠成**一个** Context，start 是 `workbench/snapshot`。我给编辑命令和 propose 工具都加了"首个检查点"（`ensureCheckpoint`），**但漏了镜像**——而镜像是任何真实会话里**第一个** workbench 事件（人先说话）。

〔事实〕浏览器控制台：

```
[web-runtime] connection sink threw: Error: conversation Context 14:workbench-treetree
  received an update before its start Match
```

整个 Context 就此报废，工作台 tab 停在空态——虽然日志里草稿好好地躺着。

**怎么改的**：镜像的 append 之前也调 `ensureCheckpoint`。配了测试钉住"任何会话的第一个 workbench 事件都是 snapshot"，三条写路径（镜像／编辑命令／propose）各一条。

**这条也只有真实浏览器跑得出来**：宿主侧单测全绿，因为宿主不折叠。

## D-26 夺刀权要能删和改名，`01 §九` 的 `accept-proposal` 签名不够

`01 §十四` 判据 1 第 4 步要求"在 proposal 卡上就地改：删 2 个、改名 1 个 → 采纳"。但 `01 §九` 的 `accept-proposal { proposalId, edits?: {field,value}[] }` **只能改字段值**，删不掉也改不了名。

先采纳再删两个也能得到同样的树，但那样**那两个节点确实进过本体**——而夺刀权的全部意义是"人在它落盘之前剪"。

**怎么改的**：加 `keptNodes?: { index, title? }[]`。给了就是"最终要的那一套"：没列到的 index 即剪掉，列了带新 title 即改名。不给＝照草稿原样采纳。UI 上每个待建节点一个标题输入框 ＋ 一个「不要这个／要回来」。

## D-27 客户端要复用宿主的纯投影层，得开一条 browser-safe 子路径

client bundle 有纯度门禁：跨包值导入一律拒绝，只放过 `INLINE_SAFE` 列的几个"无运行时身份的线/类型层"（`dsh-session`／`dsh-llm`／`dsh-tools`／`dsh-brand`／`dsh-host-apiproxy`）。

而"派生量只在 core 算一次"要求客户端**用宿主那份代码**折叠事件、算形态候选。两条规则对撞。

**怎么改的**：宿主包开一条 `./projection` 子路径，只导出纯层（model／brand／core／store／gates ＋ 事件类型），并把 `@deepseek-ai/dsh-workbench/projection` 按**精确子路径**加进 `INLINE_SAFE`，注释写明理由（包根会碰 cordis 和工具注册表，那条 entry 不会）。选它而不是在客户端重写一遍，是因为重写正是方案C 记下过教训的那件事。

## D-29 加包会顶到三处「全仓清单」，各自要手动补

新增一个注册工具的包，会让三个既有清单同时过期，而它们的报错互相无关：

| 清单 | 症状 | 补法 |
|---|---|---|
`scripts/gen-tool-catalog.ts` 的 `TOOL_PACKAGES` | README 的 tool-schema 条目要求链到 `docs/tool-catalog.md` 的锚点，而生成器只看这份手工清单（它的完整性检查只 glob `packages/*/tool-*`，我的包名不匹配，所以不会自动提醒） | 加一条 entry，`mount` 里**自己**挂 `SessionStore`（共享 harness 不挂） |

生成器还有一条好设计值得记：它会检查「entry 启动后是否真注册了工具」，并在报错里直接提示"最可能是 mount() 没满足 inject，插件停在 PENDING"——我第一次就是漏挂 `SessionStore`，一眼看出。

## D-28 加第二个 view target 会顶到 `ConversationViewSnapshotMap` 的一处类型弱点

`ConversationViewSnapshotStore.get<Target>` 对泛型 Target 取 `Map[Target]`，在只有一个成员时无害；加了 `workbench` 之后，`ui-trajectory` 的一个测试桩（自己实现 `views.get`）就编不过了——它要满足的是**所有已注册 target 的交集**。

**怎么改的**：在那个测试桩上就地窄化（`as never` ＋ 说明注释）。没有动 `ConversationViewSnapshotStore` 的契约——那是 client-runtime 的核心面，改它超出本次范围，但它是个真实弱点，第三个 target 会再撞一次。

## D-30 `SESSION_FORMAT_VERSION` 不该为「加一个事件类型」而升

**方案假设**：`06 §13.9` 与我让用户批过的裁决 B1 —— 新增 `workbench/scratch`／`workbench/focus` 两个事件类型要把 `SESSION_FORMAT_VERSION` 从 `0` 升到 `1`。

**DSH 实际**：那个常量自己的文档明写，够格升版的只有 header／envelope／核心语义／surface 的结构性变化，并且「加一个普通事件类型不构成升版 —— 词汇的增长由逐事件的 `ignorable` 覆盖」。

**怎么改的**：版本留在 `0`，一个核心文件没碰。**这条推翻了已批的 B1**；好处是本阶段完全不动 `dsh-session` 的公共面。

## D-31 `ignorable` 没有生产者 API，写「以 ignorable 落盘」是假陈述

**方案假设**：`06 §13.9` —— `workbench/scratch` 作为可跳过事件落盘，读不懂它的构建可以照常恢复。

**DSH 实际**：`Session.append` 的签名是 `(type, data, surfaceOpts?)`，`ignorable` 只在 seed 校验路径被**读**，全仓库没有任何生产者写过它。

**怎么改的**：`workbench/scratch` 保持 required-on-read（这本来就是安全的默认：读不懂就拒绝整条日志，而不是静默少一块状态恢复）。JSDoc 改成记录实况，并把那条**站得住的设计约束**写进去：跳过这些事件仍能逐字节重建已提交的树，因为提交发出的 `workbench/node-change` 带的是整个节点，而不是一个指向编辑态的引用 —— 哪天提交改成只记引用，这条性质就没了。

## D-32 `chart` 从撰写体降为派生视图

**方案假设**：`06 §2.1` 初稿把 `chart` 列进撰写体，模型可以直接写图表。

**DSH 实际**：模型撰写的数字没有可核验来源，错一格画出来的柱子看起来完全正常。

**怎么改的**：改为从 `table` 的某一列派生，判据从严 —— 该列每格都要匹配 `/^-?\d+(?:\.\d+)?$/`（拒 `8万`／`$0.4`／`约 200`／空格）。静默失效因此变成「这个视图不出现」。

## D-33 `brief` 不可删有个洞：闸门原来对空列表放行

`gateRequiredBody` 原判据是「`bodies` 里没有 `brief` 就拒」，但对 `bodies.length === 0` 放行 —— 于是可以先删到只剩 `brief`，再删掉它。

**怎么改的**：判据改成区分「`bodies` 字段缺失（还没设过内容体）」与「显式空列表（被清空）」，后者拒。

## D-34 wire 边界没校验 `op`，`planEdit` 的 default 分支其实够得着

`parseEditRequest` 只检查 `op` 是字符串就转型，所以浏览器（或手打命令的人）能把任意 `op` 送进 `planEdit`。

**怎么改的**：加 `EDIT_OPS` 白名单，并把它做成 `Record<EditRequest['op'], true>` 的派生 —— **联合里新增一个成员会编译不过**，而不是运行期才发现漏了一支。

## D-35 别的 6 个包有 13 处同一类 token bug（新门禁一开就抓出来）

我犯的那个 bug（引用一个没定义的 `--dsw-*`，整条声明在计算值期失效 ⇒ 边框 `none`、填充透明）不是孤例。`scripts/verify-design-tokens.ts` 一上线就抓出既有的 13 处：`ui-message-feedback` 4 处、`ui-settings-plugins`／`ui-jobs`／`ui-conversation`／`ui-agent-preset` 各 2 处、`ui-tool` 1 处。

**怎么改的**：记成带 `TODO(design-tokens)` 的豁免表，门禁对其余一切生效，并且**豁免项若不再出现也会失败**（防止表本身腐烂）。不去改它们，是因为每一处该换成哪个 token 是那个包自己的设计决定。

门禁自己还有过一个假阳性：`ui-primitives/HoverCard` 的 `--dsw-hovercard-bg` 是同文件里自定义的局部属性。判据是「这个引用解析得到东西吗」，所以定义集改成「主题 ＋ 消费方自己」。

## D-36 `ancestors` 对断链抛错，而浏览器合法地只折叠一段窗口

成员判定（`isConstraint`／`ideaRoots`）原来走 `ancestors`，它对「父节点不在图里」抛错。但浏览器折的是日志的一个窗口，一张卡合法地可以先于它声明的父节点到达。

**怎么改的**：拆出 `reachableChain`（容错走法），成员判定用它并答「不确定在里面」；注入与面包屑仍然拒绝断链。

**同一个洞的第二处**（这一刀新发现）：左侧树的孤儿补捞循环原来只看节点**自己**的 `region`，而想法区里的卡片自己是 `main`（是它的**根**才是 `idea`）。于是想法区根被跳过之后，里面的卡片被补捞成了一个顶层树行 —— 未确认的想法漏进了主区导航。判据改成 `ideaRoots(...).length === 0`（问包围关系，不问自身）。

## D-37 `v8 ignore` 必须是单行形式

我把一条 `/* v8 ignore next -- reason */` 排版成多行块注释后它失效了，而且已经提交了一个覆盖率红的 commit（随后 amend 修掉）。教训：改完注释格式要重跑覆盖率，不能假定它还生效。

## D-38 tag 的 key 不能只是「指向另一张表的键」

初版 `TagEntry` 只带 `key` ＋ `kind`，内容体和派生视图各在另一张表里，卡片渲染时用 `views[active.kind] ?? { kind: 'relation', edges: [] }` 兜底。这个兜底**是不可达的死代码**，而它掩盖的是真问题：tag 条和内容体区可以对「当前打开的是什么」给出两个不一致的答案，而不一致没有正确的兜底可选。

**怎么改的**：`TagEntry` 改成判别联合，**自己带上要展开的东西**（撰写体带 `body`，派生视图带 `view`）。同时把宿主的 `derivedViews()` 从「返回有哪些 kind」改成「返回算好的 view」—— 一次调用给出完整答案，调用方不必为「被告知有、却算不出来」的 kind 准备退路。（派生量只在 `core` 算一次的纪律，本来也要求是这个方向。）

## D-39 `argument` 的两种形态占一格，不占两格

见 `06 §2.6` 的〔已落地，与原设计有出入〕。形态选择是**看的方式**，不是**内容的份数**，所以它落在浏览器视图状态（按 body id 记），tag 条的五格预算不被一个论证体吃掉两格。

## D-40 新 stylesheet 撞上一条既有的滚动条 rebind 门禁

`packages/client/ui-theme/tests/scrollbar-styles.client.spec.ts` 有一条全仓规则：**在抬升面（`bg-layer-2/3` 等）上滚动的 sheet 必须重绑滚动条那对 indirection**，否则画出 l1 的滑块 —— 只在深色主题、只在那一个面上有差别，评审和浅色截图都看不出来。我的 `.card`（layer-2）里有会横向滚动的图，正中这条。

**怎么改的**：在 `.card` 上加那对重绑（自定义属性会继承到真正滚动的后代）。门禁另有两条配套检查会验重绑的**整值**拼写，所以抄不歪。

## D-41 `rescope-vendor:check` 在本阶段之前就是红的

`pnpm run hygiene` 的第一步 `rescope-vendor --check` 报 26 处 residue（`extensions/cordis-*`、`api/remotes`、若干 `ui-*`）。在 `675381b743` 的干净 worktree 上复跑，**同样 26 处**——与本阶段无关，是既有状态。本阶段照跑 hygiene 其余全部子门禁，均通过。

`packages/subagent/subagent-claude-code/tests/real-product.spec.ts` 的 3 条同理：它们真起一个 Claude Code CLI 子进程，在本机 agent 沙箱里超时。

## D-42 长流程 e2e 撞出三个真实缺口（这一刀最有价值的产出）

第 5 刀把长流程放到真组装的浏览器里跑，**一次跑出三件单元测试测不出来的事**：

| 缺口 | 症状 | 处置 |
|---|---|---|
| **新卡没有简介** | `create-child` 建出来的卡 `bodies` 是空的，tag 条上只有派生视图。人点「改这张卡」进编辑态后**没有可以写职责的地方**，而闸门同时在拒绝晋升说「你没写职责」——死循环 | `create-child` 直接建一个空 `brief`（`06 §2.2` 已补记） |
| **`brief` 与节点的 `duty` 可以不一致** | 两处都存同一段话，渲染读的是 `brief` 自己那份，而闸门读节点那份 | 渲染改成读节点；`brief` 那份由 `syncBrief()` 在提交点写下，只为读日志的人和读 `bodies` 的模型，**不当真相读回** |
| **模型提的简介会追加成第二个** | tag 条上出现两个「简介」，人无法判断职责来自哪一个 | `mergeBodies` 里 `brief` 无条件替换既有的那一个 |

## D-43 工作台 tab 在空会话里根本不存在

`ConversationSessionHeader` 在会话还是 blank（没有任何 surface 事件）时**整个头部和视图区都不渲染**，`tabs.length > 1` 也就永远不成立。于是「工作台的空态（说一句就行）」这个界面**在人真的说过一句话之前看不到** —— 空态其实是给「说过话、还没结构」的那一刻看的。

**方案假设**：`06 §4` 把空态画成第一屏。**实际**：第一屏是会话骨架自己的 Hero。

**怎么改的**：没改产品，改了理解与文档。e2e 因此在 `beforeAll` 里以宿主侧 `session.append('user/message', …)` 说出开场那句 —— 它必须存在，而在无 key 通道里打字会起一个没有 adapter 的 turn。

## D-44 `at` 时间戳不该由浏览器给

`set-tmp` 原来把整个 `NodeTmp`（含 `at`）从浏览器送过来，等于让浏览器往日志里写时间。

**怎么改的**：wire 类型改成 `TmpDraft = Omit<NodeTmp,'at'>`，`planScratch` 用宿主自己的 `clock.now()` 盖章。顺带解决了另一个问题：**空 draft（`{}`）成为「人手动进入编辑态」的表达**，于是卡片上多了「改这张卡」这个动作 —— 在此之前，进编辑态的唯一入口是模型草稿（U16 要求的人工修改因此其实是断的）。

## D-45 e2e 定位符的两个坑（会浪费很多时间，记下来）

1. **CSS Module 的 hash 是前缀**：类名长 `_0W6IWq_card`，所以 `[class*="_card_"]` 匹配不到，得写 `[class*="_card"]`。

## D-49 受控输入 ＋ 异步往返 ＝ 丢字（用户说的「根本用不了、没响应」就是这个）

## D-52 `想法` tag 曾经不是「所有卡默认都有」，而是开过想法区才出现 —— **已修**

**DSH 实际是什么（当时）**：`⁄想法` 是派生视图 tag，而派生视图的 tag 由「这张卡有没有那棵子树」算出。没开过想法区 ⇒ 没有子树 ⇒ 没有 tag。`core.ts` 里还写着一段刻意的理由：「给一个还不存在的东西挂 tag，读起来像『有想法，只是你没看』，这是错的信号」。

**方案原本假设什么**：场景 **7.1**「有一格 `想法`，**所有卡片默认都有**（U31）」。

**你怎么改的**：`derivedViews` 现在**总是**带上 `ideas` 视图（没有想法根时 `items` 为空）。

原来那段理由是被 **7.2 自己答掉的**：7.2 要求「空态说明它是干什么的（未确认／未落地）」——也就是说，不该由**隐藏 tag** 来承担「这里现在什么都没有」这个信息，该由**空态文案**承担。所以想法区拿到了自己的空态文案（`view.ideasEmpty`：「这里放还没确认、也还没落地的想头……它不进本体、对模块外也不可见」），而不是所有派生视图共用的「这里还没有可画的东西」。

**真正的理由**：放一个「还不算承诺」的想头的地方，必须在那个想头出现**之前**就在。等人先想到、再去开一个区，人已经把它放到别处去了。

**连带改的一处**：卡片的默认视图从 `tags[0]` 改成「第一个**撰写体**」。因为每张卡现在都有 `⁄想法`，一张什么内容体都还没有的卡会打开在**空的想法区**上——那等于用「这里可以放没确认的想头」回答「这张卡是什么」。现在这种卡照旧显示「这张卡还没有内容体」。

**代价**：tag 条多了一格常驻。三格上限之外的进 `⋯`，所以根节点（简介 ＋ `⁄子模块` ＋ `⁄全局约束` ＋ `⁄想法`）会有一格落进溢出菜单。

## D-59 「按模块切分上下文」在阶段 1 只切了依赖集，没切会话历史 —— 而且**插件层切不了**

**你在真页面上撞到的**：在子模块里说话，没有新会话，带着完整历史。

**DSH 实际是什么**：模型请求的历史是 `this.session.deriveMessages()`（`agent-loop/src/agent.ts:341`）——**整条会话日志**折出来的线性 transcript。`moduleId` 只写在 `workbench/utterance` 上，`grep` 全包：**没有任何地方用它筛过任何进入模型的东西**。工作台的「按模块」只作用在两处：

1. **右栏显示**（`talkLines` 按 focus 过滤）——是个视图；
2. **工具返回的依赖集**（`dependencySet(graph, nodeId)`）——这一半确实是按模块的。

**方案原本假设什么**：`06 §6.3` 选了 R-a，并写着「AI 只看得到这个模块的依赖集」。**这句话是过度声明**：它只对**工具结果**成立，对**请求整体**不成立。同一节确实老实记了「会话历史仍是一条，所以斜率照旧」，但把它当成**只是成本问题**。

**它不只是成本问题——有一条保证是假的**：场景 7.6／7.7「想法对模块外不可见」。`renderSkeletonIndex` 把想法从**依赖集**里滤掉了，但在想法区里**说过的话**是普通 `user/message`，照旧躺在 transcript 里，之后每一次请求都带着它。场景自己在 7.6 旁边写过：「界面藏起来而依赖集里还在，是最坏的一种 —— 人以为它没影响，它却在影响。」现在是同一件事的另一条泄漏路径：**依赖集干净，历史泄漏**。〔代码层确定〕；〔待检验〕模型实际会不会用它。

**为什么不能像 `§6.3` 设想的那样「用 request-context 插件过滤请求历史」**：

- `agent/pre-step` 的 `messages` 只是**这一步新领到的 inbox 消息**（`this.inbox.claim(...)`），不是历史，改它改不到历史。
- `llm/stream(options, next)` 的 `next()` **不接参数**，监听器无法改写 `options` 再往下传；而且请求是 `deepFreeze` 过的。
- 最关键的一条：`agent-loop/src/invariant.ts:39` 有一条**运行时不变量**——
  ```
  if (JSON.stringify(options.messages) !== JSON.stringify(session.deriveMessages()))
    fail('… diverges from the dispatch-time durable derivation (log-reconstruction desync)')
  ```
  **请求的消息必须与日志折出来的完全相等。** 任何在插件层偷偷过滤历史的做法都会当场撞这条不变量——这正是根 `AGENTS.md`「Model-visible ⟺ logged」那条规则的执行者。

**所以 `§6.3` 那句「按模块过滤请求历史比新建会话便宜得多」是错的**：它在 token 上便宜，在架构上不便宜——它要动 `deriveMessages` 的投影规则（`core/session/src/surface.ts` 的「THE per-node projection rule」）或者动 agent-loop，两者都是**核心改动**，不是插件增量。

**你怎么改的**：**没改实现**（这是阶段 2 的架构裁决，不该我单方面做）。改的是文档：修正 `06 §6.3` 的过度声明，并把「想法不可见性目前未被强制」写进两个包的 Known Limitations 与场景 7.6／7.7 的判定。

**两条真实可选路，代价都记在 `06 §6.3`**：R-b（每模块真子会话，`openSubagent`）要客户端跨会话读取面；或者**把切分做成落盘的投影**（像 compaction 那样用一个事件记录作用域，让 `deriveMessages` 认它）——这条保住不变量，但要动核心投影规则。
