## 一、范围与目标

### 阶段 0 目标（POC）

把方案C 的**最小闭环**跑通：**空页一句话 → AI 出候选骨架 → 人剪枝 → 晋升门 → 已承诺**，且全程满足方案C 的两条硬约束：

- 人的编辑**即时落盘、零等待零花费**（§4.1 写盘权按发起者分）
- AI 只能 `propose`，产出**必须经人裁决**才进本体（§4.1、§7.1）

### 做（阶段 0）

| # | 项 |
|---|---|
| 1 | 内容模型：骨架九字段（v1 只启用标题/parent/职责/成熟度/来源/正文）+ 全局单调 `rev` + `last_rev` |

| 8 | 客户端「工作台」tab：节点树（左）+ 焦点区（右）+ 形态渲染器骨架 + proposal 卡 + 裁决按钮 + 仪表行 |

```
└──────────────────────────────────────────┴──────────────────────────────────────────┘

  模块会话（内部创建，阶段 0 先不做，工具契约已就位）
  AI 在任意会话里调 workbench_read_nodes → 读依赖集展开；调 workbench_propose → 草稿事件
```

**数据流铁律**（对应方案C §3.6、§5.2）：
- **本体 = 陈述**：节点树只存"关于世界的陈述"。
- **一手层 = 痕迹**：原话/事件不可改只追加。
- **本体变更的唯一入口是 `workbench.edit`（人）与三个工具（AI），统一走 append 事件**；`rev` 在每次落盘 +1。
- **派生量只在 `core.ts` 算一次**：依赖集/失效判定/形态候选（方案C §5.2 的教训）。

## 四、数据模型（`model.ts`）

```ts
// 成熟度取值域定死（§3.1）：新增档位 = 数据迁移，v1 不做
type Maturity = 'thought' | 'idea' | 'committed' | 'rejected'

// 骨架九字段（v1 启用 6 个，其余占位）
interface NodeFields {
  title: string                       // 一行内说清
  parent: string | null               // 层次归属；根=null
  duty?: string                       // 职责（有子节点时强制）
  maturity: Maturity                  // §2.1 闸门按它作用
  source: 'human' | 'ai' | { sourceId: string }   // ◆人 / △AI / 指向一手层
  body?: string                       // 散文态正文
  // v2 预留占位（零成本，§十-1）：
  verifyCriteria?: 'none' | 'wish' | 'executable'
  action?: 'none' | 'wish' | 'executable'
  // 开放字段（字典外不允许，见闸门）：
  fields: Record<string, { value: string; sourceId?: string }>
}

interface WorkbenchNode extends NodeFields {
  id: string                          // 品牌化 Branded<'NodeId'>
  lastRev: number                     // 最后落盘时的全局 rev
  createdAt: number
}

// 一手层条目（只追加；open 枚举，v2 加执行记录不迁移）
type FirstLayerEntry =
  | { kind: 'utterance'; entryId: string; text: string; createdAt: number }   // 原话
  // | { kind: 'material'; ... }  // 阶段 0 只留位

interface WorkbenchMeta {
  rev: number                         // 全局单调
  fieldDictionary: Record<string, { semantic: string; shape: string }>  // 字段词典（v1 预置空 + 内置字段白名单）
}
```

**存储形态**（对应调研的会话事件路径）：
- **本体**：`workbench/snapshot` 事件存全量快照（含 `meta.rev`），`workbench/node-change` 存增量。冷启动从最近快照重放增量（快照策略见 §六）。
- **一手层原话**：`workbench/utterance` 事件，只追加。
- 事件落哪个会话：**工作台会话**（用户建的一个普通会话，其日志即本体+一手层的持久化载体）。

## 五、事件契约（`events.ts`，SessionEventMap 扩展）

所有事件 data 须 JSON 可序列化（`session.append` 强校验）。`@mode emit` + 每个 payload `@param`（仓库惯例）。

```ts
declare module '@deepseek-ai/dsh-session/types' {
  interface SessionEventMap {
    /** 全量快照：冷启动/定期 checkpoints（whole-value，prefer checkpoint） */
    'workbench/snapshot': { rev: number; nodes: WorkbenchNode[]; meta: WorkbenchMeta }
    /** 一次落盘（唯一写事件；人/AI 两条路径都汇聚于此） */
    'workbench/node-change': {
      rev: number                    // 落盘后新 rev
      actor: 'human' | 'ai' | 'system'
      op: 'create' | 'update' | 'move' | 'delete' | 'promote' | 'reject'
      node: WorkbenchNode            // 变更后全量节点（whole-value，便于 UI/AI 直接消费）
      invalidation?: string[]        // 1 跳作废清单（依赖了该节点的在跑任务/草稿；阶段 0 仅返回给编辑端）
    }
    /** 一手层原话：不可改只追加 */
    'workbench/utterance': { entryId: string; text: string; createdAt: number }
    /** AI 草稿（AI 唯一写路径的产物；不落本体） */
    'workbench/proposal': {
      proposalId: string
      targetNode: string | null
      title: string
      summary?: string
      body?: string
      fields?: { name: string; value: string; sourceId?: string }[]
      newNodes?: { title: string; parent?: string; body?: string; fields?: { name: string; value: string }[] }[]
      createdAt: number
    }
    /** 人裁决（accept 触发 node-change，reject/edited 记此处） */
    'workbench/verdict': {
      proposalId: string
      outcome: 'accepted' | 'rejected' | 'edited'
      rev: number                    // 裁决时刻的全局 rev
      note?: string
    }
  }
}
```

**不变量**：`snapshot.rev ≤ 最新 node-change.rev`；同一 `(proposalId)` 只有一个 start（proposal 事件）且至多一个 verdict；`node-change.op='promote'` 时 `node.maturity` 必须从非 committed 变为 committed。

**批处理语义（rev = 提交单位）**：一次采纳/一次落盘 = 一个 `rev`。一次多节点采纳产生的 N 个 `node-change` 事件**共享同一 rev**（原子性保在落盘这个动作上，§7.1），被采纳节点的 `lastRev` 相同；store 与 UI 按"同 rev 事件批"整体应用。

**source 变更规则**：人编辑 AI 生成的字段后，该字段 `source` 置为 `'human'`（△账"正文 x% 由 AI 生成且未改一字"的数据基础）。

**原话镜像机制（冷启动的模型可见性，硬要求）**：自定义会话事件不进模型上下文——`add-utterance` 落的事件 AI 看不到，而 `workbench_read_nodes` 只接受节点 id。因此：插件监听工作台会话的 `user/message` 事件，**逐字镜像**为 `workbench/utterance` 事件。用户在普通输入框说话 → 文本进模型上下文（AI 可见）且一字不改入一手层（事件保真），满足"原话一字不改入库"。

## 六、投影 store（`store.ts`）

- **输入**：工作台会话的 `session/event` 流（`ctx.on('session/event')`，只处理 `workbench/*`）+ 启动时从持久化日志读（`sessionPersistence` 或 `sessions.get().history`）。
- **折叠规则**（对齐 conversation-node cookbook：whole-value checkpoint 优先）：
  - `snapshot` → 整体替换内存树 + `meta.rev`
  - `node-change` → 按 op 增删改；`rev = node-change.rev`
  - `proposal`/`verdict` → 挂到 `proposals: Map<proposalId, {...}>`
  - `utterance` → 追加到一手层表（内存只保留索引，正文在事件里按需取）
- **快照策略**：每 50 次 node-change 或每次晋升后 append 一个 `snapshot`（幂等、可重放）；冷启动 = 最近快照 + 其后增量重放。上限内重建时间可测（否证测试）。
- **读取面**（宿主内部，供工具/API 用）：`getNode(id)` / `dependencySet(id)` / `children(id)` / `constraints()` / `proposal(id)`。
- 阶段 0 **不落第二份磁盘副本**（本体只活在事件日志里，符合"一个事实源"）。

## 七、核心纯函数（`core.ts`，唯一派生量实现处）

全部无 I/O、同输入同输出，配否证测试（方案C §9.3 硬要求）。

### 1. 依赖集 v0 `dependencySet(nodeId): DependencyItem[]`

| 种类 | 注入什么 | 何时 |
|---|---|---|
| 自己 | 全部字段 | 总是 |
| 父链 | 祖先的 `职责`+`正文` | 总是 |
| 全局约束区 | `G-` 子树全部条目 | 总是 |
| 依据引用 | `fields[].sourceId` 指向的一手片段 | 有引用就有 |
| 骨架 | 全局节点索引（id+标题+成熟度） | 总是 |

```ts
type DependencyItem = { kind: 'self'|'ancestor'|'constraint'|'source'|'skeleton'; id: string; rev: number; content: string }
```

### 2. 展开 `expand(items): string`（喂给 AI 的文本；v1 仅 join + 头注）

### 3. 失效判定 `invalidate(nodeId): string[]`（v1 只做 1 跳）

反向索引（实时转置，不落盘）：查"引用了该节点或被它约束的节点"→ 返回受影响节点 id 清单（阶段 0 返回给编辑端显示；调度器在阶段 1 消费）。

### 4. 形态候选 `shapeCandidates(node): Shape[]`（§3.5）

v1 只实现两个：`只有 标题+正文 → 段落卡`；`有子节点 → 子节点列表`（树）。其余形态（表/关系图/论证图/流程）类型占位，UI 渲染器 v2 再补。

### 5. 字段登记校验（供闸门用）`isRegisteredField(name): boolean`

内置白名单（骨架字段）+ `meta.fieldDictionary`。v1 字典为空，任何新开放字段都触发"未登记"。

## 八、闸门（`gates.ts`，§9.1 v1 清单的子集）

| 闸门 | 档 | 作用区 | 挂点 |
|---|---|---|---|
| 未登记字段 | 拒绝 | 仅已承诺区 | `propose` 的 fields 校验；`edit.update-field` 校验 |
| 提炼无依据 | 拒绝 | 仅已承诺区 | `fields[].sourceId` 必须指向已存在的一手层条目 |
| 悬空引用（parent/依据） | 拒绝 | 全区 | 所有写路径 |
| 无环 | 拒绝 | 全区 | move 时沿父链检查 |
| 否决无理由 | 拒绝 | 全区 | edit.reject / promote→rejected 需 `note` |
| 模块无职责（有子节点无 duty） | 提示（不阻塞） | 仅已承诺区 | promote 时检查，缺则返回"需补"清单 |

每条闸门配**否证测试**：注入它应当拒绝的情形，确认真拒（§9.3）。

## 九、人的编辑通道（决策点 D1 的落法）

### 模式 A（默认）：仓库内置 → RPC 端点畅通

在 apiproxy `RpcMethodMap` 注册 `workbench.edit`（外加 `workbench.ready` 读初始状态）。客户端 `ctx.connection.api` 调用。这是阶段 0 的主路径。

**`workbench.edit` 契约**（zod schema，op 判别联合）：

```
op: 'create-child'   { parentId: string|null, title: string, body?: string }
  | 'update-field'   { nodeId, field: string, value: string, sourceId?: string }
  | 'rename'         { nodeId, title: string }
  | 'move'           { nodeId, parentId: string|null }
  | 'delete'         { nodeId }
  | 'promote'        { nodeId, maturity: 'committed'|'rejected', note? }
  | 'accept-proposal'{ proposalId, edits?: {field: string, value: string, sourceId?: string}[] }   // 见下"夺刀权"
  | 'reject-proposal'{ proposalId, reason: string }
  | 'add-utterance'  { text: string }

返回: { ok: true, rev: number, invalidation: string[] }
       | { ok: false, code: 'GATE_UNREGISTERED_FIELD'|'GATE_DANGLING_REF'|'GATE_CYCLE'|'GATE_NO_REASON'|'GATE_MISSING_DUTY'|..., message }
```

执行：校验（闸门）→ `rev += 1` → `session.append('workbench/node-change', …)` → 返回。**人侧路径不触发任何模型调用、零花费、零等待**（§4.1）。

**夺刀权语义（accept-proposal 的硬要求，§7.1）**：proposal 卡内容**就地可编辑**（人改的是草稿副本，不落盘、不花钱、不等待）；人点 [采纳] 时，`accept-proposal` 流程为：**应用 edits → 对最终内容重跑闸门（重新预演）→ 通过则原子采纳**（同 rev 批处理落盘，见 §五）。改出问题（未登记字段/悬空引用）当场拒绝并指出，杜绝"人改完带病落盘"。

### 模式 B（备选，将来提取 standalone bundle 时验证）

standalone 插件无自定义 RPC 通道（RpcMethodMap/typert 是仓库内机制）。备选：
1. `ctx.commands.register()`（已确认开放）——把编辑编码成斜杠命令（文本体验，阶段 0 不采用）；
2. 动态 cordis 的 `dynamicCordisRunner.invoke` + host-half `harness.handle`——需验证 standalone 可达性；
3. 最稳：**保留在仓库内作为内置包分发**（预发布期仓库欢迎新包）。

## 十、工具契约（`tools.ts`，模型可见面）

系统提示词新增 workbench 章节（`ctx.systemPrompt.section`，order 自定义）：说明内容模型、成熟度、`propose` 是唯一写路径、引用一手层。

### 1. `workbench_read_nodes`（读：依赖集机械展开）

```ts
parameters: { nodeId: string }   // 读哪个节点的依赖集
output: { node: {...}, dependencySet: DependencyItem[], constraints: string[] }
执行: core.dependencySet(nodeId) → 展开文本 → 返回
```

### 2. `workbench_propose`（AI 唯一写路径）

```ts
parameters: {
  targetNode?: string,
  title: string,
  summary?: string,
  body?: string,
  fields?: { name, value, sourceId? }[],
  newNodes?: { title, parent?, body?, fields? }[],   // 候选骨架树（冷启动场景）
}
执行: gates 校验(未登记字段/无依据，按目标区成熟度) → append 'workbench/proposal' → { proposalId }
```

### 3. `workbench_promote`（晋升门）

```ts
parameters: { nodeId: string, maturity: 'committed'|'rejected', note?: string }
执行: 晋升门校验（补登记字段/无依据/模块职责）→ 缺项返回 { blocked: ['MISSING_DUTY', …] }（让 AI 经 propose 补）
      → 通过则 append node-change(op:'promote') → { rev }
```

三个工具的 `execute` 均使用 `exec.signal` 取消、返回 canonical JSON（`adding-a-tool.md` 契约）；`presentCall/presentResult` 定义卡片（propose → `workbench/proposal` 卡）。

## 十一、客户端 UI（`packages/client/workbench/`）

### 装配

- `conversation.view` list 槽注册一个 `workbench` tab（keyed，类似 trajectory）；tab 内自绘，不碰聊天流（路径 A）。
- `conversationEvents` 注册 `WorkbenchTreeDefinition`（ConversationNodeDefinition）：`match` 认 `workbench/*` 事件，`start`=snapshot，`update`=node-change/proposal/verdict → 产出树 State。
- 裁决：proposal 卡 [采纳] [改] [不要] → `workbench.edit`（accept/reject-proposal）。

### 组件树

```
WorkbenchTab
├─ WorkbenchTree          左：折叠树（一行一节点：标题+成熟度记号 念头○ 想法△ 已承诺◆ 已否决✖）
│   └─ 工作集钉顶          最近触碰 4 个节点（客户端 last-touched 列表，v1 内存态）
├─ FocusPane              右：选中节点
│   ├─ NodeHeader         标题/职责/成熟度/来源
│   ├─ NodeBody           正文（MarkdownText）
│   ├─ FieldTable         字段表（+ 登记状态标记）
│   ├─ ShapeSwitcher      形态渲染器骨架：段落卡 | 子节点列表（v1 两种，占位其余）
│   └─ ProposalList       挂在本节点的 proposal 卡：summary/body/fields/newNodes **就地可编辑**（草稿副本，改不落盘）+ [采纳][不要] 裁决按钮
└─ Meter                  底部仪表行：第N轮｜累计rev｜△账（"正文 x% 由 AI 生成且未改一字"，v1 计数版）
```

### 数据流

- 下行：`conversationEvents` 折叠 → `useSession`/tab 内 store → 渲染（无需 scan 事件窗口）。
- 上行：交互 → `ctx.connection.api.workbench.edit(...)`（模式 A）→ 宿主 append 事件 → mux 推回 → 折叠更新。
- 选中状态：tab 内受控 state（v1 不持久化）。

## 十四、验收走查（对应方案C §14 判据 1、3）

### 判据 1：冷启动到第一个承诺

1. 新建工作台会话，打开「工作台」tab：左区空，焦点区提示「说一句就行」。
2. 人在**输入框（composer）**说一句话 → 文本进模型上下文 + 插件镜像为 `workbench/utterance` 事件（原话一字不改入一手层，§五）。
3. 人在同一会话发消息请 AI"出候选骨架"（**阶段 0 由人触发；最终态为巡检流自动跟随，见 §十七-3**）→ AI 调 `workbench_propose`（newNodes 5 个顶层节点，各 title+duty，source=ai）→ 工作台 tab 出现 proposal 卡。
4. 人剪枝（夺刀权）：在 proposal 卡上**就地改**（删 2 个、改名 1 个）→ [采纳] → accept-proposal 重跑闸门 → **同一 rev 原子落盘**（5 个 node-change 共享该 rev）→ 树出现。
5. 人把一个节点[晋升]（edit.promote）→ 闸门检查：有子节点缺 duty → 返回 blocked 清单 → 人补 duty 后晋升成功 → 成熟度=已承诺。**晋升门只在此刻集中付摩擦**（§2.1）。

### 判据 3：人自己改一句话，即时落盘零等待零花费

1. 人在焦点区直接改正文（edit.update-field）→ 立即生效，无模型调用。
2. `rev` 递增；`workbench/node-change` 已落日志（UI 可验）。

## 十七、已知偏差（Phase 0 与完整设计的诚实差距清单）

阶段 0 交付的是**"前段"（思维导图段）+ 晋升门**；"后段"机制缺席。逐条声明，防止"走通即完整"的错觉（方案B 教训）：

| # | 偏差 | 阶段 0 现状 | 阶段 1 落点 |
|---|---|---|---|
| 1 | **巡检流缺席**（方案C §2.4 论证它是架构必需——落盘即时与一致性检查的共存机制） | 一致性只在写路径上检查（闸门）；落盘后无任何异步检查 | 巡检流：事件触发 + 预算仪表 |
| 2 | **依赖集失效/调度器缺席** | `node-change.invalidation` 只返回给编辑端展示，无人消费 | 调度器（§5.4）消费作废清单 |
| 3 | **冷启动骨架由人触发**，非巡检自动跟随 | 人在会话里请 AI 出骨架 | 巡检流特例：utterance 事件 → 自动骨架建议（§11.1 未写明触发方，见下方"方案C 悬点"） |
| 4 | **全局约束区只能注入空集** | 无提升机制；跨天场景（§11.2 门票 vs 不能卖票）**不可演示** | 巡检任务类型 2：约束提升提议 |
| 5 | **模块隔离/多会话故事缺席** | 工作台=单一会话视角（tab 只折叠本会话事件）；上下文全部在一条会话里 | 模块会话卡 + 跨会话联动 |
| 6 | 工作集/选中态为客户端内存态 | 不持久化 | 工作集上移到宿主事件（§5.1 它还要喂父层会话） |
| 7 | 仪表只有计数版，无「新会话」手闸、无巡检暂停开关 | — | §12.1 #14 完整版 |

**方案C 悬点（不阻塞，但需你补一句话）**：§11.1"AI 出候选骨架"未写明由哪条流触发；流③巡检的触发三条件（模块静止∧rev 变过∧建议未满额）在冷启动时空转（尚无模块）。建议在方案C 中明确：冷启动骨架 = 巡检流特例（一手层新增原话事件触发一次骨架建议，计入巡检预算账）。
