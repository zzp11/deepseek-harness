# 把「方案C：念头到落地」做成 DeepSeek Harness 插件 —— 可行性调研

## 一、结论先行

**可行，且 DSH 的架构（"一切皆插件"）几乎是为这类产品准备的。** 方案C 的每一个核心机制在 DSH 上都有现成对应物或干净的自建路径：

| 方案C 机制 | DSH 对应物 | 现成程度 |
|---|---|---|
| 一手层（原话/材料，只追加） | 自定义会话事件（`SessionEventMap` 合并扩展，自动持久化） | ✅ 现成 |
| 模块会话流（上下文按模块切分） | 多会话 + agent presets + `agent.followup()` | ✅ 现成 |
| AI 巡检流（事件驱动、后台） | `ctx.on('session/event')` + `ctx.jobs` / `ctx.subagents` / `schedule` | ✅ 现成 |
| AI 产出须经人裁决（草稿-裁决） | 自定义工具 + `ctx.approval` / `ctx.userQuestions`（UI 有现成 PendingApproval） | ✅ 现成 |
| 单页三区工作台 UI | 客户端插件 + UI 槽位系统（`sidebar`/`conversation`/`details`/`shell.overlay`/`conversation.chat.node`） | 🟡 可行，UI 是最大工作量 |
| 依赖集 / 失效判定 / 反向索引 / 闸门 | 插件内纯函数，无框架依赖 | ✅ 自由实现 |
| 调度器（等待/去抖/作废） | 插件内逻辑 + `ctx.jobs` 后台任务 | ✅ 自由实现 |

**最大风险不在技术，而在范式**：DSH 的 Web GUI 是"会话/聊天"范式，方案C 是"工作台"范式。如何嵌（或替换）是唯一的硬决策点，见 §四。

## 二、逐项证据

### 1. 插件包怎么写（服务端）

- 最小形态：一个包导出 `name` / `inject` / `apply(ctx, config)` 三件套（例 `packages/extensions/tool-cordis/src/index.ts:26-35`）；配置用 schemastery `z.object(...)`（例 `packages/web/web-search-deepseek/src/index.ts:46-74`）。
- 自定义工具：`ctx.tools.register(defineTool({name, description, parameters, output, execute(args, exec), presentCall?, presentResult?}))`，`execute` 里可用 `exec.signal` 取消（`docs/cookbook/adding-a-tool.md`）。工具 schema 自动进系统提示词，Code Mode 里 `await tools.<name>()` 免集成可用。
- 注册即 effect：插件卸载自动注销，天然热重载（`docs/cookbook/extension-cookbook.md`）。

### 2. ctx 上可用的服务（AI 层全有）

| 服务 | 用途（对应方案C） |
|---|---|
| `ctx.llm.stream(options)` | 插件可直接发模型请求 —— 巡检、委派、提炼的底层通道（`packages/llm/llm/README.md`；实例 `session-title-llm`） |
| `ctx.sessions.create/get` + `session.append(type, data)` | 每模块一个会话、追加自定义事件（`packages/core/session/src/index.ts:604-655`） |
| `ctx.agents` → `agent.followup()/inject()/steer()` | 唤醒 AI 干活 / 注入上下文 / 转向（core/agent） |
| `ctx.approval.request(...)` | "AI 产出须人裁决"：返回 allowed-once/rejected，UI 现成渲染（`interaction/user-approval`，审计事件自动落盘） |
| `ctx.userQuestions.ask(...)` | 就地一行式提问（方案C 的"就地一行，非弹窗"） |
| `ctx.jobs.start(...)` | 后台任务（`<kind>-N` 作业 id、owner 隔离、onJobDone 回调） |
| `ctx.subagents.startContinuable(...)` | 后台子代理，settle 后通知父级 |
| `ctx.schedule` | 定时提醒，到点 `agent.followup()` 投递 —— "巡检"的定时范式（`packages/schedule/schedule/README.md`） |
| `ctx.settings` / `ctx.credentials` | 配置节 + API key 管理 |
| `ctx.storage`（JSON/SQLite 后端 + domain KV） | 插件自有非会话数据的持久化（`packages/storage/`） |
| `ctx.workspaceRegistry` | 按目录的项目注册（"项目工作台"容器） |

### 3. 自定义事件 = 一手层

- `SessionEventMap` 是 merge-extensible 的（`packages/core/session/src/types.ts:231-333`），插件 `declare module` 加自己的事件类型，`session.append()` 即写入不可变日志、自动 JSONL/SQLite 持久化、实时推给前端（`/api/events.mux`，`api-proxy.ts:3475-3493`）。
- 这就是方案C 的"一手层只追加、不可改"的现成载体；`裁决.jsonl` 也可以就是 `workbench/verdict` 事件流。
- 注意：仓库外插件的自定义事件在持久化读路径上需要 `ignorable` 标记（`known-event-types.ts`）；若走"内置包"路线则自动进清单。

### 4. 插件怎么装进用户的 dsh

- 官方发布路径：`dsh plugin --profile <name> add <pkg>`，bundle + profile 机制（`docs/user/develop/basic/publish.md`）；git 安装需 `prepare` 脚本（官方示例 [turtle-ui](https://github.com/deepseek-harness/turtle-ui)，**已证明第三方 UI 插件可行**）。
- 用户级补丁：`~/.dsh/profiles/<profile>/cordis.patch.yml` 加一行 `insert`，**支持 HMR 热重载**（`packages/boot/app-boot/src/index.ts:226-251`）。
- 甚至模型自己可以装载插件（self-modification：`cordis_define/cordis_run/...`，`packages/extensions/cordis-host-runner`）。

### 5. Web UI 扩展面（客户端插件）

- 客户端插件：`package.json` 声明 `dsh.client` + `exports["./client"]`，tsdown client 预设打包，运行时经 `window.__ModuleLoader__` 装载；改动**无需重建 web 壳**，`pnpm run dev:web` watch 即 HMR（只对 client-plugin 生效）。
- 槽位系统（`packages/client/ui-layout/src/client/index.ts:34-84`）：
  - `sidebar`（左列，独占）、`conversation`（中列，独占可整体替换）、`details`（右列，独占）、`shell.overlay`（全屏浮层，叠加式）。
  - `conversation.session`（单会话体，可整体自绘）、`conversation.view`（tab 环，可新增"工作台"tab，类似 trajectory）、`conversation.chat.node`（keyed 业务行渲染）、`tool.call.toolview`（**按工具名给自定义工具挂专属卡片**）、`conversation.input.dock`（仪表区）、`conversation.composer`（输入栏接管链）。
  - `root` 槽明确禁止注册（会替换整个框架）。
- 设置面板：`installSettingsSection` + `settings.section` 槽（命名空间须进宿主暴露白名单 `WEB_SETTINGS_NAMESPACES`）。
- 后端扩展三条路：apiproxy `RpcMethodMap` 新方法 / typert `@Remote` / 转发事件白名单 `API_REMOTE_FORWARDED_EVENTS`。

## 三、方案C 十四个机制的落法（逐条）

| 方案C 条目 | 落法 | 工作量 |
|---|---|---|
| 1. 骨架九字段 + `last_rev` | 插件数据模型（存 `ctx.storage` KV 或工作区文件） | 小 |
| 2. 全局单调 `rev` | 插件内计数器，每次落盘 +1 | 小 |
| 3. 开放字段 + 字段词典 + 未登记字段闸门 | 插件代码；闸门挂在 propose 工具的 execute 里 | 小 |
| 4. 一手层三类（只追加） | 自定义会话事件流（原话/材料/执行记录=三类事件） | 小 |
| 5. `依据` 指向一手层 | 事件 id 引用 + 悬空检查 | 小 |
| 6. 全局约束区 `G-` 子树 + 提升机制 | 数据层特殊子树 + 巡检任务类型 | 小 |
| 7. 依赖集 / 展开 / 失效判定 / 反向索引 | 插件内纯函数（无框架依赖，可写否证测试） | 中 |
| 8. 调度器（等待/去抖/作废/并发上限） | 插件内状态机 + `ctx.jobs` 起后台任务 | 中 |
| 9. 会话生命周期（版本变则换会话） | 模块=真实会话；`rev` 变则新建/重开该模块会话，裁决事件重新注入 | 中 |
| 10. 写盘权按发起者分 | 人的编辑走自定义 API 端点（不经工具管线）；AI 只有 propose 工具 + approval | 小-中 |

**补充（子代理 C 确认）：** `ctx.fs` 无 watcher，现成文件监听均为插件自接 chokidar（settings-file、skill-filesystem local-provider 先例）。巡检触发建议以**自定义会话事件**为信号（节点变更即 append 事件），比监听文件更直接；只有材料导入等文件侧变更才需要 chokidar。
| 11. 导入三段式（入库/索引/提炼） | 材料=事件或文件；切片纯函数；提炼=propose | 中 |
| 12. 草稿就地叠加、可编辑 | 客户端 UI：`tool.call.toolview` 自定义卡片或工作台 tab | 大（UI） |
| 13. 内容 hash 前后端比对 | 前端 store + 后端 rev/哈希，插件自建 | 小 |
| 14. 仪表 + △账 | `conversation.input.dock` 渲染 + 自定义事件记账 | 中（UI） |

## 四、三个关键决策点

### 1. UI 范式：嵌入 vs 替换（唯一的大决策）

- **路径 A「嵌入」（推荐先做）**：不动现有聊天界面。工作台作为 **`conversation.view` 的一个新 tab**（类似 trajectory）+ `tool.call.toolview` 自定义工具卡片 + `conversation.input.dock` 仪表。用户在一个会话里既能正常聊天，又能切到"念头树"视图。改动小、复用聊天能力（composer、approval UI、历史）。
- **路径 B「替换」**：注册进 `conversation` 独占槽，整体替换中栏为"左树+右焦点+对话栏"三区。最接近方案C 原意（"一个 HTML 页面"），但要自绘消息流、输入栏、裁决 UI，工作量翻倍以上。
- 建议：先 A 后 B；A 走通即满足"念头→已承诺→可验证"的核心闭环，B 是形态打磨。

### 2. 数据通道：会话事件 vs 文件

- 方案C 本体（`内容.yaml`）有两种存法：
  - **会话事件**：节点变更 = `workbench/node-change` 事件。自动持久化、自动推前端、天然满足 DSH 的"模型可见 ⟺ logged"原则（`AGENTS.md:107`——**AI 读到的任何内容必须能从会话日志重建**）。
  - **`ctx.storage` KV**：适合大文本/材料原件，但 AI 读取需经工具并记事件。
- 建议：本体走会话事件（append-only 事件流 + 快照事件），材料原件走 `ctx.storage`/工作区文件。这恰好复刻方案C"本体存陈述、一手层存痕迹"的分层。

### 3. 权限与写权

- 人的编辑：自定义 API 端点（RpcMethodMap），不经工具管线 → 天然"零摩擦、零成本"，完全绕开 AI 权限体系（方案C §4.1 的核心诉求）。
- AI 产出：`propose` 工具 → 结果落 `workbench/proposal` 事件 → 前端就地渲染 → 人裁决（approval 或自定义按钮）→ 采纳才写本体。
- 这正好实现方案C"防 AI 乱写强度不降、人侧零阻塞"的双轨写权。

## 五、风险清单

| 风险 | 等级 | 说明/对策 |
|---|---|---|
| UI 工作量（工作台 vs 聊天范式） | **高** | 路径 A 控制在 1 个 tab + 若干卡片；路径 B 是大工程 |
| "模型可见⟺logged"约束 | 中 | AI 读节点内容必须经工具 + 会话事件；不能只读文件 |
| `ctx.fs` 沙箱 | 中 | 插件写自有文件可能受沙箱限制；优先自定义 API + 存储服务 |
| 巡检成本失控 | 中 | DSH 无现成预算控制；用 `ctx.llm` usage 统计 + 事件记账自建 △账（方案C 本就要求） |
| 白名单机制 | 低-中 | 新 API 端点/转发事件/设置命名空间都要进对应注册表；作为仓库内置包（PR）或动态 cordis 装载 |
| 事件类型注册 | 低 | 内置包自动进 `KNOWN_SESSION_EVENT_TYPES`；外部包需 `ignorable` 标记 |
| 测试成本 | 中 | DSH 测试政策严（snapshot/coverage）；但插件包可按自身节奏，MockBackend 模式可复用（方案C §12.4 本来就有） |

```
阶段 0（POC，1 个服务端包 + 1 个客户端包，~1-2 周/人）：
  - 服务端：内容模型 + 3 工具（workbench_propose / workbench_read_nodes / workbench_promote）
    + 自定义事件族 + 1 个自定义 API 端点（人的编辑）
  - 客户端：conversation.view 一个"工作台"tab，渲染节点树 + 裁决按钮
  - 验收：冷启动一句话 → AI 出候选骨架 → 人剪枝 → 晋升门（对应方案C §14 走通判据 1）

阶段 1（核心机制，~1-2 周）：
  - 依赖集 + 展开/失效/反向索引；调度器（等待/去抖）
  - 巡检流：监听 node-change 事件 → ctx.jobs 后台巡检 → 建议事件 → UI 记号
  - 导入三段式（粘贴文本 + .md/.txt）
  - 验收：方案C §14 判据 3/4/5（人即时落盘零等待、走开不打断、等待队列省钱）

阶段 2（形态打磨，按需）：
  - 路径 A→B 演进（工作台 tab → 替换中栏三区）
  - 字段词典 UI、△账仪表、材料引用账、过期建议账
  - 验证判据/执行动作（v2 预留，方案C §十）
```

## 八、用户追问的两个设计点（Q&A）

### Q1：能支持复杂样式吗（选中模块 → 主页面展示文本/流程图/框架图）？

**能，全部在客户端插件的 React 视图里实现。** 槽位系统只提供"座位"（工作台 tab / 替换会话体 / details 列），座位里画什么完全是插件代码：

- 文本：现成 `MarkdownText`（`packages/client/ui-primitives`）。
- 流程图/框架图/关系图/论证图：仓库**无内置图引擎**，但无阻碍——客户端插件打包时 `CLIENT_EXTERNALS` 平台表只豁免 DSH 模块，第三方库（mermaid / reactflow / dagre 等）会打进插件自己的 client bundle（`packages/client/tsdown.client.ts`）。`npm i reactflow` 即可。
- "形态由字段派生"（方案C §3.5）＝一个 `switch(node.fields)` 渲染器：有序步骤→流程、层次 parent→嵌套框/树、立场/论据→关系图、同构列表→表。
- 选中状态：工作台 tab 内受控 React 状态；可写回自定义事件持久化。
- 代价：重库增大插件 bundle（mermaid ~2MB），客户端无硬上限。

### Q2：会话能变成"附属于内容模块的小卡片"吗？能跨会话联动吗？

**能。** 结构：一个可见的"工作台会话"承载整棵树（视图换成工作台 tab）；**每个模块的 AI 会话 = 插件内部创建的真实会话**（`ctx.sessions.create` + `ctx.agents.create`，独立 agent/日志/上下文）。工作台 tab 渲染迷你聊天卡片（⟳ 运行中 / ⚑ 建议 / ⚠ 过时），输入走自定义 RPC（`workbench.prompt(moduleId, text)`）→ 插件找到该模块 agent → `followup()`；后台任务结果以自定义事件回流刷新卡片。

跨会话联动三层机制：

| 层 | 机制 | 落法 |
|---|---|---|
| 数据层 | workbench store（节点树+`rev`+依赖图），host 侧单例跨会话共享 | `ctx.storage` KV / 会话事件 |
| 上下文层 | 依赖集注入：模块会话发起时注入相关模块事实 | `agent.inject()`（持久、logged）；`rev` 变→上下文作废重注入（§5.5） |
| UI 层 | A 模块变更实时反映到 B 模块卡片 | `events.mux` 推所有会话事件（`api-proxy.ts:3475-3493`）；保险：自定义 RPC 轮询 / 转发事件白名单（`API_REMOTE_FORWARDED_EVENTS`） |

限制：① 现 GUI 同一时刻只渲染一个会话对话面，迷你卡的历史/输入要插件自写（复用 `session.history` RPC）；② 每模块一个 agent = 独立 LLM 成本，巡检 △账插件自建。
