## 三、后端（宿主包 `@deepseek-ai/dsh-workbench`）

### 3.1 模块划分与「派生量只算一次」的落点

```
src/
  brand.ts       NodeId / SourceId / ProposalId 三个 Branded 不透明 id
  model.ts       内容模型类型 ＋ 常量（骨架字段名、成熟度标签、G- 根 id）
  events.ts      SessionEventMap 的 5 个成员 ＋ 载荷类型
  store.ts       事件 → 投影（applyWorkbenchEvent / projectWorkbench / 快照策略）
  core.ts        ★ 派生量唯一实现处
  gates.ts       闸门：6 个 gate 函数 ＋ 汇总与渲染
  edit.ts        人的写路径（纯计划函数）
  propose.ts     AI 的写路径（纯计划函数）
  tools.ts       三个工具的 schema 与执行
  prompt.ts      系统提示词片段
  present.ts     工具调用的 UI 渲染意图（纯函数）
  checkpoint.ts  ensureCheckpoint：任何写路径的第一件事
  projection.ts  ★ 浏览器安全的再导出屏障
  invariant.ts   运行时不变量伴生
  index.ts       装配：name / inject / Config / apply
```

**`core.ts` 是唯一派生处**（`90-方法论前提` 的硬条，依据是实测过的失效：同一事实算两遍给出两个数字）。
它导出：`requireNode` `children` `ancestors` `constraints` `isConstraint`
`dependencySet` `treeIndexSet` `citedSourceIds` `expand` `invalidate`
`shapeCandidates` `isRegisteredField` `nextRev` `structuralHealth`
＋ 三个渲染助手 `renderNodeFully` `renderNodeDuty` `renderSkeletonIndex`。

**闸门、工具、编辑计划、客户端一律只消费，不自算。** 客户端也不例外 —— 见 §4.2。

### 3.2 内容模型（`model.ts`）

骨架字段实况：**启用 6 个，留位 2 个**。

| 字段 | 阶段 0 | 说明 |
|---|---|---|
| `id` `title` `parent` `duty` `maturity` `source` `body` | **启用** | `duty`＝职责，是全局骨架里代替正文的东西（§5.1） |
| `verifyCriteria` `action` | **留位** | v2 才实现，字段名与三档取值域已定死（§十-1） |
| `fields`（开放字段表） | **启用** | 每项 `{ value, sourceId? }`，`sourceId` 即 `依据` |
| `lastRev` | **启用** | 该节点最后一次落盘时的全局 `rev` |
| `createdAt` | **启用** | 记账 |

`Maturity = 'thought' | 'idea' | 'committed' | 'rejected'` —— **取值域定死**，
新增档位会迫使已存节点重判成熟度，那是数据迁移（§3.1）。
`MATURITY_LABELS` 把四档映射成 `念头／想法／已承诺／已否决`，**模型与人读同一组词**。

`GLOBAL_CONSTRAINT_ROOT_ID = 'G-'`：约束区是内容树里的一棵特殊子树，不另立存储（§3.4）。

`Shape = 'paragraph-card' | 'child-list' | 'table' | 'relation-graph' | 'argument-graph' | 'flow'`
—— 六种形态的**类型已全定**，而 `shapeCandidates` 阶段 0 只答前两种。这是阶段 1 的入口。

### 3.3 事件族（`events.ts`）

`SessionEventMap` 声明合并，5 个成员：

| 事件 | 载荷 | 语义 |
|---|---|---|
| `workbench/snapshot` | `WorkbenchSnapshot` | **完整检查点**：`{ nodes, firstLayer, proposals, meta }` |
| `workbench/node-change` | `WorkbenchNodeChange` | 一次落盘里的一个节点：`{ rev, actor, op, node }` |
| `workbench/utterance` | `WorkbenchUtterance` | 一手层「原话」：人说的话，一字不改 |
| `workbench/proposal` | `WorkbenchProposal` | AI 的草稿，**不进本体** |
| `workbench/verdict` | `WorkbenchVerdict` | 人对草稿的裁决：`accepted / rejected / edited` |

**快照是完整检查点而非增量**（D-08）：`10 §五` 的快照载荷描述与 `§六` 的冷启动要求互相矛盾，
取完整检查点这一读法，因为客户端的折叠引擎要求一个 Context 的 `start` 事件能独立起算。

**`ChangeOp = 'create' | 'update' | 'move' | 'delete' | 'promote' | 'reject'`**，
`ChangeActor = 'human' | 'ai' | 'system'` —— `actor` 是 △账的数据源，机械可判定（§4.1 写盘权按发起者分）。

**模型可见 ⟺ 已记录**：进过模型请求的每一样东西都能从会话日志重建。
`workbench/utterance` 就是为这条而存在的 —— 人在对话框里说的话本身是一手层条目。

### 3.4 投影（`store.ts`）

`applyWorkbenchEvent(state, event)` 就地折叠，`switch` 按判别标签分派，**`default` 抛错**
（`WORKBENCH_EVENT_TYPES` 之外的事件不该进来）。
`projectWorkbench(events)` 从 `latestSnapshotIndex` 起算，只重放它之后的事件。
`shouldSnapshot(state, change, everyChanges)` 决定何时落检查点，`snapshotOf(state)` 造它。

**`changesSinceSnapshot` 存在投影里而不是另算**：快照策略与投影吃同一份状态。

### 3.5 闸门（`gates.ts`）

6 个 gate 函数，`GateCode` 六值，每个 finding 带 `blocking: boolean`（拒绝档／提示档）。

| gate | 码 | 档 | 作用区 |
|---|---|---|---|
| `gateDanglingRefs` | `GATE_DANGLING_REF` | 拒绝 | 全区 |
| `gateNoCycle` | `GATE_CYCLE` | 拒绝 | 全区 |
| `gateRegisteredFields` | `GATE_UNREGISTERED_FIELD` | 拒绝 | **仅已承诺区** |
| `gateEvidence` | `GATE_NO_EVIDENCE` | 拒绝 | **仅已承诺区** |
| `gateReason` | `GATE_NO_REASON` | 拒绝 | 全区 |
| `gateDuty` | `GATE_MISSING_DUTY` | **写入时提示、晋升时拒绝** | 仅已承诺区 |

`runNodeGates(graph, node, { promoting })` 是唯一入口，`blockingFindings` 过滤出拒绝档，
`renderFindings` 出人与模型都读的那段文字。

**`gateDuty` 双档是 `10` 内部矛盾的处置**（D-06）：`§八` 写它是提示档，`§十四-12` 要求晋升门拦下缺职责。
两处都对，因为它们说的是两个时点 —— 于是 `GateContext.promoting` 这一位决定档位。

**摩擦集中在晋升这一个动作上**（§2.1）：念头区只有结构性闸门（悬空、成环、否决无理由），
`未登记字段` 与 `提炼无依据` 只在已承诺区生效。

**否证测试是硬要求**（§9.3）：每条闸门都先注入一个它应当拒绝的情形、确认它真的拒，
才声称它有效 —— `tests/gates.spec.ts`。

### 3.6 人的写路径：走命令通道，不走 RPC

**通道选择**（D-01）：`ctx.commands.register('workbench-edit')`，客户端以
`ctx.remote.commands.execute(sessionId, '/workbench-edit {...}')` 程序化派发。
`recordInput: false`，`CommandResult.sourceEventSeq` 带回它 append 的事件 seq。

为什么不是新 RPC 方法：那要改 `rpc-map.ts`（近 60 天 60 次改动的热文件）。
`commands.execute` 已经是 `@Remote`，**不需要网关侧任何改动**。

**顺带证到一件事**（D-21）：手打 `/workbench-edit {...}` 进输入框会**当作普通聊天发给模型**——
`ui-commands` 是靠键入 `/` 弹出的候选面板拦截的，不是在提交时拦。
所以"命令通道的文字体验差"这条反对意见不存在：人根本碰不到这条通道，它只被程序化派发。
代价照实记：我是靠误发一次真实请求发现的，那次花了钱。

`EditRequest` 是一个判别联合，9 支：

```
create-child        parentId | null, title, body?
update-field        nodeId, field, value          # field ∈ EDITABLE_SKELETON_FIELDS 或开放字段
rename              nodeId, title
move                nodeId, parentId | null
delete              nodeId
promote             nodeId, maturity: committed|rejected, note?
promote-to-constraint  nodeId
accept-proposal     proposalId, edits?, keptNodes?
reject-proposal     proposalId, reason
```

`planEdit(state, request, clock)` 是**纯函数**，返回 `EditPlan`：
`{ ok: true, events, rev }` 或 `{ ok: false, failure }`，
`EditFailure` 三类：`missing`（指不到）／`gate`（闸门拒绝）／`request`（请求本身不合法）。

**一次提交一个 `rev`**：`commitNodes` 把一次编辑涉及的所有节点写成同一个 `rev`。
判据 1 要求"删 2 个改名 1 个再采纳，结果是 3 个节点同一个 rev"，靠的就是这条。

**`keptNodes` 是为夺刀权加的**（D-23）：`10 §九` 原本的 `accept-proposal` 只能改字段值，
而 `§十四-1` 要求人在采纳前剪枝。先采纳再删能得到同样的树，
但那两个被删的节点**确实进过本体**，事后无法与"从未进来"区分。
所以剪枝必须发生在提交之前：`keptNodes` 在场时它**就是**被采纳的集合，缺席的下标即被剪。

### 3.7 AI 的写路径：三个工具

| 工具 | 语义 | 并发 |
|---|---|---|
| `workbench_read_nodes` | 读依赖集的机械展开 | 只读，可并发 |
| `workbench_propose` | 提草稿。**不进本体** | — |
| `workbench_check_promotion` | 问"这个节点现在能不能晋升"，返回闸门结论 | 只读，可并发 |

**第三个工具不是 `10 §十-3` 写的 `workbench_promote`**（D-11）：
一个能让节点晋升的工具与 `§一`「人始终主刀、模型产出必经人裁决」直接冲突。
晋升是人的动作；模型该有的能力是**预先知道会不会被拦**，于是改成只读的 `check_promotion`。

**`nodeId` 在 `read_nodes` 上是可选的**（D-24，端到端抓出来的真 bug）：
树为空时模型拿不到任何合法 `nodeId`，而骨架索引原本只作为依赖集的一项出现。
真实的 DeepSeek 在这里猜了一个 id、收到 `no node G-`、转而去翻我的源码与会话日志，
**烧了 288K 输入 token 也没提出一个草稿**。修法三处：`nodeId` 可选（不传只回约束区＋树索引，
`treeIndexSet`）、`requireNode` 的错误话术改写、提示词第一句就是"先不带参数调一次"。

### 3.8 提示词与原话镜像

`prompt.ts` 出系统提示词片段：工具怎么用、四档成熟度是什么、闸门会拦什么。
**从模型的视角写**，不含 UI／传输／实现词汇。

原话镜像：人在对话框里说的每句话，同时以 `workbench/utterance` 落一份进一手层。
两个坑都在真实运行里踩到过：

- `session.append` **在一次 append 正在发布时拒绝重入**，所以镜像必须 `queueMicrotask` 推迟（D-19）。
- 镜像通常是一个真实会话里的**第一个** workbench 事件，而客户端把整族折成一个 Context、
  要求 `start` 必须是检查点 —— 浏览器控制台 `received an update before its start Match`，
  整个 tab 空着，虽然日志里草稿好好躺着（D-25）。修法：镜像也先 `ensureCheckpoint`。

`checkpoint.ts` 的 `ensureCheckpoint(session, state)` 因此成为**三条写路径共同的第一件事**，
并有测试断言"任一会话的第一个 workbench 事件必定是快照"。

### 3.9 不变量伴生（`invariant.ts`）

仓库惯例要求每个包拥有 `./invariant`，检查一条**被拥有的关系**，而不是服务或方法是否存在。

本包的不变量注册在 **`internal/dispatch`** 而不是 `session/event`（D-20）：
`session/event` 的失败被会话存储按观察者逐个容纳，抛出的错永远到不了任何人面前 ——
注册在那里的不变量**永远不会报告**。`internal/dispatch` 上抛出的错会传播。

不变量本身写成**无期限形式**：不说"多久之内必须发生"，只说"若发生了写入，则……"。

### 4.1 折叠：一个 Context 折整族

`workbenchTreeDefinition`：`match` 认下全部 `workbench/*` 事件，
`workbench/snapshot` 是 `start`，其余是 `update`；`update` 不改它折叠自的状态（返回新对象）。
`workbenchViewDefinition` 把折出来的树发布到 `views.get('workbench').tree`。

**为什么一个 Context 折整族**，而不是每类事件一个：树是一个整体，
分开折等于让客户端把五个流再拼一次 —— 那就是第二个事实源。

### 4.2 客户端复用宿主的纯投影层

客户端 `import { ... } from '@deepseek-ai/dsh-workbench/projection'`。

`projection.ts` 是宿主包的一个**浏览器安全子路径**，只再导出
`brand` `core` `gates` `model` `store` 与 `events` 的类型 —— 纯函数与类型，不碰 cordis、
不碰会话存储、不碰 I/O。包根不可能进浏览器包（它要 cordis、命令注册表、工具注册表）。

装载侧：`packages/client/tsdown.client.ts` 的 `INLINE_SAFE` 加了这一条，
**按精确子路径**匹配（`@deepseek-ai/dsh-workbench/projection$`），包根不在其列。

**这条是为了不让派生量算两遍**（D-13）：依赖集、成熟度记号、形态候选如果在浏览器里重写一遍，
就是 `90-方法论前提` 记下的那个实测失效——同一事实两个值。
候选做法是"客户端自己实现一份折叠"，被否掉的理由就是这个。

### 4.3 状态与写回

`store.ts` 四片：`selected`（当前焦点）／`drafts`（人在草稿上改的字段值）／
`nodeChoices`（人对草稿里每个待建节点的取舍与改名）／`refusal`（最近一次拒绝的话术）。
**全部是视图状态，不落盘** —— 改草稿不落盘、不花钱、不等待（§7.1）。

写回：`index.ts` 的 `inject(sessionId)` 给出五个回调，每个都是一次
`ctx.remote.commands.execute(...)`；宿主答的是它 append 的事件 seq，
**改动本身从事件流回来**，tab 从不信自己的乐观副本。

拒绝档的处置：宿主的拒绝话术原样显示给人（`refusal`），失败字符串不本地化，
与客户端的错误面策略一致。

## 五、判据实测

`10 §14` 十五条里，阶段 0 覆盖第 1 条与第 3 条。**两条都在真实 DeepSeek 上走过**（3081 端口，浏览器实跑）：

## 七、端到端抓出的三个真 bug
